# Legacy Well Assessment v3 — Phase 1 (Core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the v2 register with one local-first Next.js application (Portfolio, Wells, Well page with Assessment/Construction/History, Score flow, Methodology reference, Project settings, Import/Export, print reports) on a single data model, with the scoring engine's numerics unchanged and the five existing wells migrated losslessly.

**Architecture:** A pnpm workspace with two packages. `packages/engine` is framework-free TypeScript: the ported scoring engine, recommendation, suggestions, staleness, the wellbore parser/renderer, and the Zod domain schemas. `apps/web` is a Next.js App Router client-side app that talks to a `Store` interface; Phase 1 ships `LocalStore` on IndexedDB (Dexie) with full-project JSON export/import. No backend, no sign-in (parked per spec §11.1); a local reviewer profile stamps every assessment and audit event.

**Tech Stack:** pnpm 10 workspaces · TypeScript 5.7+ strict · Next.js 16 (App Router) · React 19 · Tailwind 4 · shadcn/ui · Zod 4 · Dexie 4 · @tanstack/react-table 9 · Vitest 5 (+ fake-indexeddb, @testing-library/react) · Playwright 1.64+ · GitHub Actions

**Spec:** `docs/superpowers/specs/2026-10-20-v3-rebuild-design.md` (approved 2026-10-20, hosting and identity parked). Earlier normative specs it keeps: `2026-07-28-unified-risk-methodology-design.md`, `2026-08-07-recommended-action-override-design.md`, `2026-08-07-wellbore-schematic-design.md`.

## Global Constraints

- Engine numerics are unchanged: golden vectors V1–V5 from `tools/scoring.test.js` and `scoring.js GOLDEN_VECTORS` pass verbatim; `computeWell` rounds L and C to 2 decimals, `riskIndex` to 2, `cell = round(L) × round(C)`.
- Methodology rev `2.0.0` (11 params, 7 L / 4 C, weights per `methodology.json`) is the seed; bands Low 1–4 `#1fbf75`, Moderate 5–9 `#f0a93b`, High 10–16 `#e85a4f`, Very High 17–25 `#a8324a`. Rank colours are used for rank only.
- Canonical units: metres, WGS84 decimal degrees, ISO-8601 UTC. Display: L, C, Risk Index at one decimal; cell as an integer; depths in m with ft toggle. Stored values keep 2 decimals.
- Unknown is explicit: a parameter has no default score; a suggestion is never auto-applied; finalise requires a justification for every non-Unknown score.
- Assessments are append-only: a `final` is never edited; re-assess creates a new record with `supersedesId`.
- No secret, token, or backend call anywhere in Phase 1. Reviewer identity is the local profile and is stored as `reviewerName` (string) only.
- Light theme default; Inter for UI, JetBrains Mono for UWIs/depths/numbers with tabular numerals.
- Enums (from v2 `CSV_COLS`): Well Type `Oil Producer | Gas Producer | Injection | Disposal | Strat Test | Observation | Unknown`; Trajectory `Vertical | Deviated | Horizontal | Unknown`; Status `Active | Suspended | Abandoned (P&A) | Orphaned | Unknown`; Classification `Type 1` … `Type 9`.
- v2 CSV template headers remain importable (exact strings in Task 16).
- Branch work on `feat/v3-phase1`; one commit per task step that says "Commit". The v2 site stays live on `main` until Task 18's Pages switch is confirmed.

## Review Focus

1. **A CSV containing the same licence twice, or a licence already in the project** → the second occurrence updates the first, the report says "updated", nothing is duplicated (Task 16 tests `upsert: duplicate licence within file` and `upsert: existing licence`).
2. **A well with no coordinates** → Wells table, Portfolio, and Score flow all work; distance shows "—"; no plume suggestion (Task 3 test `suggest: no lat/lon → no plume`; Task 11 e2e `score flow works for a well without coordinates`).
3. **Methodology revision changes between saving a draft and finalising it** → finalise recomputes with the current methodology and stamps the current revision; the draft shows a banner (Task 6 test `finalise stamps current revision, not the draft's`).
4. **Importing a project export into a browser that already holds that project** → wells merge by licence, assessments and audit events are appended only when their ids are new, counts in the result are correct, nothing duplicates (Task 6 test `importProject merge is idempotent`).
5. **Deleting a well that has final assessments** → requires typing the licence, removes its assessments, and writes one audit event carrying the full snapshot so it can be recovered from an export (Task 9 e2e `delete well requires typed licence` and Task 6 test `wells.remove snapshots assessments in audit`).
